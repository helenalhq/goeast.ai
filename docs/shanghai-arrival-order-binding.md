# Shanghai Arrival Check — same-order delivery candidate

This is the formal workflow, not the earlier fictional intake demo. The candidate does not activate real sales, send customer mail, or use the existing Preview rehearsal schema.

1. **Submit.** The signed-in buyer enters Shanghai arrival date, flight, exact hotel name/address, and optional non-sensitive constraints. An immutable V1 trip, buyer identity, price and consent copy version are created server-side. The buyer can reopen the order through their account session.
2. **Verify and quote.** The operator checks the operating flight, date, terminal and hotel branch from appropriate sources; unresolved trips remain unpayable. The operator sets a quote expiration and explicit delivery deadline before arrival. The buyer sees the verified result and accepts the quote before checkout. This slice does not promise an automatic two-hour or 12-hour SLA.
3. **Confirm payment.** One hosted checkout is bound to that exact order and version. Browser returns never mark it paid. The signed callback requires a fresh Creem checkout and transaction readback; base USD price and gross payment (including explicitly reported tax) are validated. Discounts, amount/identity mismatches and out-of-window payments do not prepare a report; ambiguous payments require operator review. If checkout creation times out before binding, never create a second session blindly. Find the original session/callback in Creem support tools before deciding whether a new order can be created. This candidate does not yet automate that recovery.
4. **Render and review.** Use the protected operator queue (GET /api/arrival-orders/operator) and fetch that exact order with ?id=UUID. Use its packetTrip unchanged in the report recipe. The operator researches and reviews content, not just syntax; route, switching rules, backup preferences, Chinese address and source ledger must fit the actual trip. See scripts/fixtures/arrival-order-packet.qa.json for the recipe format. Run python scripts/render-arrival-order.py recipe.json EMPTY_OUTPUT_DIRECTORY to create report.pdf, address.png and manifest.json. Dependencies: Python 3, ReportLab, Pillow, DejaVu and Noto Sans CJK. Use purpose=qa for Test, purpose=reviewed only for a real reviewed order. Do not include customer email, payment details or booking codes in the packet. Check all pages and Chinese text before approval.
5. **Approve exact bytes.** POST to the operator endpoint with ?id=UUID and JSON {action:"approve",manifest:…,pdf:BASE64,png:BASE64}. It checks order/version, verified trip and preferences, file bounds and checksums, and only accepts the paid state. Do not edit the manifest or transfer files from another order. Approved bytes are immutable. Buyer-only download serves the sealed PDF and PNG; revoked orders cannot download again. Already-downloaded files cannot be recalled. Customer mail remains unimplemented in this slice.
6. **Refunds/disputes.** A separately signed exact transaction notification blocks download and records the event. It applies before or after the paid callback, and a replay cannot reopen access. Source: https://docs.creem.io/code/webhooks.md. Register only on this product's dedicated handler after controlled acceptance; keep existing GoEast products and callbacks unchanged.
