# GoEast P1 Live: staged production integration

Decision: **no Live offer from the current Preview build**. Baseline `d1b7a5b` verified one signed sandbox $1.99 payment and full refund on one synthetic QA order; the real report model, delivered-artifact persistence, and removal of an already-generated report were not exercised. The older Mock run is separate. Production on P0 `8eb9500` is unaffected. The current P1 QA code is hard Preview/QA/Test only, and cannot become Live through an environment toggle.

## Sequence and launch gates

1. **Prove the deliverable without charging customers.** Use authorized synthetic inputs and a separately approved bounded model run. Keep the refunded Test order terminal. Verify the exact cast survives payment, the explicit generate action receives its expected Azure deployment and produces a valid report, failure returns the order to a retryable state without another payment, and the owner can reopen the same saved asset. Verify another QA account cannot list, fetch, or modify it. Verify a fully refunded delivered report is suppressed and that a late paid event cannot restore it. Use offline fixtures for injection/concurrency; one hosted run alone does not prove those.
2. **Add Live as a separate production adapter and least-privilege store.** Reuse the existing versioned order/report shapes and transition invariants (`pending → paid → generating → delivered`; linked full `refunded` terminal). Choose the physical schema separately; require a production-only report login restricted to this feature, server-derived Auth UUID and owner predicate for every user read or mutation, and datasource-level tenant isolation/negative tests. Do not use the QA role, QA rows, QA recovery markers, P0 subscriptions or a broad service-role key. Bind one immutable public purchase intent to one provider checkout/order/transaction; ensure callbacks and model-generation leases persist correctly under races and crashes. Test at least two accounts, unique IDs, RLS or an equivalent boundary, owner-checked `Cache-Control: private, no-store` on private reads and errors, and retry/refund race behavior on an isolated fixture and staging. Decide retention, deletion, support and data-processing disclosures for user questions/action notes before storing real input.
3. **Create Live billing only after safe launch controls exist and are approved.** Keep the Production app dark initially. Use a separately verified Live Store/SKU, $1.99 USD one time, no renewal, clear tax totals, and a P1-only minimal Live key/secret. Hard-pin the Live API and canonical www origin and verify the authenticated product response (Creem wire mode `prod`, not the app label `live`) before creating a session. For tax-exclusive checkout, require the fixed 199-cent USD base plus the separately reported tax to equal the paid gross; do not mistake tax for a price change or accept mismatched totals. The signed callback is independent of the browser return, bounded before parsing, and only applies matching mode, exact product/amount, owner-derived existing order, checkout and transaction. Verify nonmatching Test/Pro events are harmless. In the authorized deployment operator preflight, inspect both P1 and existing P0 event subscriptions without changing P0. Same-store refund fan-out can make old P0 log `pro_monthly` even though its refund branch does not mutate Pro; exclude such unclassified logs from both purchase/refund metrics and use mode/SKU plus order/transaction evidence. Then reconcile partial/unknown refunds by exact linked provider transaction and cumulative signed/provider-confirmed totals and do not auto-revoke; a verified matching full refund is terminal. Define a separate signed dispute/chargeback reconciliation path before launch: record and triage exact Live transaction evidence, preserve the order, and do not auto-revoke unless a verified full refund applies or an explicitly defined dispute-hold policy applies. Test hold, resolution and delayed/replayed events without treating a dispute notification as a full refund. Verify Production ingress without making a sale and smoke-test P0 before and after dark deployment.
4. **Prevent standalone sales and define unlinked-payment handling.** Creem documents that its provider-generated storefront can display a merchant’s products; this does not prove GoEast has one enabled. Verify disabled/excluded storefront and short-link surfaces before any listing. The Live product form did not offer a safe draft; creation can make a SKU sellable immediately. Do not create it while there is no safe launch control, list it on a public storefront, generate a public short link, or publish a generic provider link. Only the authorized GoEast checkout should originate a provider session with exact local intent and correlation metadata. An unlinked signed Live payment never grants an artifact or alters Pro; reconcile provider order/transaction against authorized support evidence, flag for review, and use a separately authorized refund/support workflow if it cannot be fulfilled. Never create an entitlement from email, price or payment mode alone.
5. **Define repeat purchases and expired holds before opening sales.** The Preview fingerprint is terminal after refund. Specify whether a future deliberate repurchase is allowed; if so use an explicit new, owner-confirmed purchase intent after proving the prior attempt is terminal and no original provider session can still accept payment. Never mint a concurrently payable second session to clear a stale hold. A known unpaid-expired provider checkout may be closed through a reviewed reconciliation policy; an ambiguous or paid provider outcome must be matched to the original order, not expired locally or charged again. Check timeout-after-create, delayed webhook, simultaneous browser attempts, stale provider link, full refund and deliberate repurchase as separate cases.
6. **Separate new sales from existing obligations.** After dark deploy, verification, and separately authorized sale scope, enable only a named, authenticated canary account before considering a public phase. When pausing new sales, continue signed settlement/refund, existing owner delivery and recovery for paid orders. Full off is for before any sale or after outstanding obligations have been reconciled and a replacement is ready. Keep of-age purchase reconciliation, generation failure, stale claim and refund metrics separate for Live vs Test and P0; no questions, emails, private links or customer IDs in analytics. Exposure counters must not fold Preview/Test into the Live experiment.

## Default-off production runtime configuration

The isolated Live runtime uses canonical `https://www.goeast.ai`, Vercel `production` and Git `main`, the exact new Live P1 product, and Creem wire mode `prod`. Configure only server-side Production settings:

| Layer | Variables | Safe behavior |
| --- | --- | --- |
| Production location and product | `DECISION_REPORT_LIVE_ORIGIN`, `DECISION_REPORT_LIVE_CREEM_PRODUCT_ID` | Canonical www and exact Live SKU; reject known Test and existing Pro SKU. |
| Storage | `DECISION_REPORT_LIVE_DB_PROJECT_REF`, sensitive `DECISION_REPORT_LIVE_APP_DATABASE_URL`, sensitive `DECISION_REPORT_LIVE_CALLBACK_DATABASE_URL` | Supavisor verified TLS with separate `p1_live_app` and `p1_live_callback` logins; exact scoped role and storage guard in same transaction as each RPC. No datastore fallback. |
| Creem | Sensitive `DECISION_REPORT_LIVE_CREEM_API_KEY` and `DECISION_REPORT_LIVE_CREEM_WEBHOOK_SECRET` | Distinct from P0/Preview. Fixed authenticated host. Exact Live signed ingress `/api/decision-report/webhook`; subscribe only checkout, refunds and dispute reconciliation. |
| Model | `DECISION_REPORT_LIVE_MODEL_CREDENTIAL_SOURCE=existing_azure` or `dedicated`; optional/explicit `DECISION_REPORT_LIVE_MODEL_DEPLOYMENT`; `DECISION_REPORT_LIVE_MODEL_BUDGET_ACK=true` only after budget approval | Existing source uses already-configured server-only Azure endpoint/key/model in place (optional deployment override); dedicated source requires its own `DECISION_REPORT_LIVE_MODEL_ENDPOINT` and sensitive `DECISION_REPORT_LIVE_MODEL_API_KEY` plus explicit deployment. Both require verified official Azure HTTPS `/openai/v1` endpoint, 1600 completion tokens, 25s/no retries, three durable per-order attempts, no fixture or unconfigured fallback. Provider-side spending budget is still required; acknowledgment is not a financial limiter. |
| Dark/settlement | `DECISION_REPORT_LIVE_SETTLEMENT_ENABLED=true` only after authorized full configuration | Unset is dark and no external calls. Status/history and callback settlement can remain available when new orders or generation are paused. |
| New sales | `DECISION_REPORT_LIVE_CHECKOUT_ENABLED=true` and `DECISION_REPORT_LIVE_PHASE=canary` + `DECISION_REPORT_LIVE_CANARY_OWNER_ID`, or `phase=public` + `DECISION_REPORT_LIVE_PUBLIC_ENABLED=true` | Default off. Requires all model, signing and two store credentials. Pause new sales by disabling checkout, **not** settlement. An already issued provider link may remain payable; keep callbacks and reconciliation available. |

Current fingerprint stays terminal; there is no automatic repurchase or ambiguous retry on Live. An unresolved checkout stays pending for operator reconciliation, never expires based only on an application timeout or silent provider lookup. Terms/privacy/support review and product-host allowlist evidence remain launch gates.

Production endpoint tests in this deliverable use fake responses and an isolated fixture; they did not contact hosted Creem, Azure or customer data. The provider adapter currently permits the documented `https://checkout.creem.io/ch_…` hosted session form only; if provider-approved live evidence shows another legitimate form, bind it to exact product/checkout and add a fixture, rather than generic old links or any host wildcard. The app is not released by these changes.

### Temporary presale runtime probe

While checkout and public sales are off, configure only a separate, randomly generated 32-byte lowercase-hex bearer in sensitive Production `DECISION_REPORT_LIVE_READINESS_TOKEN`. Call only the canonical authenticated `GET /api/decision-report/readiness` with that bearer in the Authorization header (never in the URL, pasted into a ticket, or echoed into logs). Revoke it after the check. A 200 `{"ok":true}` means both actual constrained login connections passed the read-only catalog guard, the authenticated Creem product matches the active Live one-time USD 199-cent SKU, and the configured Azure endpoint/key/deployment and budget acknowledgement have the required **shape**. A valid bearer receives 503 if any condition fails; other requests receive 404. This does not verify provider callback signing end to end, product storefront visibility, checkout URL shape, Azure authorization or spend. It makes no model call, creates no payment, reads no customer data, and works with settlement off or on.

For the separate ingress-only check: keep sales off, enable settlement only, then use a Creem-signed generic callback sample **only if confirmed to omit a correlatable paid order/transaction**. An ignored 200 confirms reachability and signature acceptance, not fulfillment. Do not send/replay real or plausibly correlatable Live payment/refund payloads as a probe.
