## Data and telemetry

- Owned by verified auth UUID; one durable order and independently identified artifact per unchanged question/cast and test mode. Unchanged repeated requests reuse the pending checkout or report. A report snapshot cannot be delivered until provider-confirmed payment (or explicit mock pay for the isolated QA path). Captured lines and source are resolved independently of the model, and only delivered reports expose private content.
- New events use `offer_id=decision_once`: `offer_viewed`, `checkout_started`, `checkout_created`, `payment_confirmed`, `delivery_succeeded`, `delivery_failed`, `refund_confirmed`. The merchant/provider IDs needed for reconciliation are opaque; no question/body, email, private URL, or account ID is logged. Server P1 events are tagged as QA and test/mock; internal diagnostic warnings are not payment. Unlinked refund tombstones are not counted.
- [Creem checkout contract](https://docs.creem.io/api-reference/endpoint/create-checkout), [webhook payloads](https://docs.creem.io/code/webhooks), [transaction contract](https://docs.creem.io/api-reference/endpoint/get-transaction).
- A failed TEST checkout after the pending claim logs one server-only `test_checkout_failed` diagnostic: `provider` (transport, invalid JSON, or non-success HTTP status), `correlation` (names of mismatched fields only), or `save` (write error or no matching row). This does not log response bodies, URLs, IDs, credentials, or raw errors and does not identify whether Creem committed an ambiguous request. The pending hold remains in force; these diagnostics neither reconcile the existing claim nor authorize creating a new session.
- Local SQL fixtures (no network or app database): install `@electric-sql/pglite@0.5.17` with a disposable npm prefix, then run `PGLITE_MODULE=/absolute/prefix/node_modules/@electric-sql/pglite/dist/index.js node scripts/verify-decision-order-sql.mjs`. Run application tests with `npm test`.

## Approved alternative: same-project QA schema and database login

This is an alternative to steps 1–2, not a change to the original isolated-project migration. It uses the same Supabase project as Auth, but a different PostgreSQL schema and a **dedicated database login**, never a production service-role key. It is manual and Preview-only. No production offer, subscription, RLS policy, Data API schema list or app migration needs to change. Use synthetic questions only.

1. **Before touching the hosted database**, run the scoped SQL fixture below and confirm the intended project reference, PostgreSQL identity, and designated QA UUID through an authorized operator. Use the read-only `supabase/decision-report-scoped/preflight-public.sql` to list ACL blockers without reading production rows. Review `supabase/decision-report-scoped/001.sql`; replace the one UUID placeholder in a local working copy, never commit it. The transaction requires the designated UUID already exists in `auth.users` and stops on a name collision, reachable non-QA data privileges (including column privileges), non-QA create/connection privileges, or callable non-QA SECURITY DEFINER functions. For example, a deployed function retaining default PUBLIC EXECUTE may block this option. **Stop if a check trips; do not revoke production privileges, disable RLS, or delete any existing object to make it pass.** A separate database remains the fallback.
2. The first commit creates `goeast_p1_qa` as a **NOLOGIN** role with no access-granting role memberships, concurrent connections limited, and a private schema of the same name; ownership stays with the operator. Do not add the schema to the Data API exposed list or grant the role to the authenticator. Check the role/schema, privileges, no role memberships other than PG16+ operator governance with ADMIN but neither SET nor INHERIT, and project limits before setting a short-lived password securely, e.g. the authorized operator's interactive `psql \password goeast_p1_qa` over verified TLS; set an explicit expiry and enable LOGIN only for the QA window. Do not paste passwords or credentialized URLs into chat, shell history, logs or commits. Verify identity and `select goeast_p1_qa.decision_qa_isolation_ok('<verified UUID>'::uuid);` over the same transaction-pooler login before configuring the app. If the result is not true or the pooler cannot authenticate with that role, turn LOGIN back off and stop. The app rechecks on the same transaction before every operation. On the hosted project, do not attempt write/deny probes against production tables; use catalog checks, and run actual negative writes only on the disposable fixture.
3. Use the **project's actual Supavisor transaction-pooler host**, e.g. `aws-0-us-east-1.pooler.supabase.com`, port `6543`, database `postgres`, and username `goeast_p1_qa.<project-ref>`. Build the dedicated URL from that login with URL-encoded password, no query/fragment. The adapter requires verified TLS, checks the same project reference as the existing Supabase Auth URL, uses no named prepared statements, and refuses production mode. Store URL as sensitive in the **develop Preview only**: `DECISION_REPORT_STORAGE=scoped-postgres`, `DECISION_REPORT_SCOPED_DATABASE_URL`, `DECISION_REPORT_PREVIEW_QA_USER_ID`, `DECISION_REPORT_MODE=mock`, `DECISION_REPORT_ENABLED=true`. Do not mix with the separate Supabase service-role settings. Deploy the same tested commit to Preview only and verify that mock order creation, delivery, reopening and refund work, and another signed-in account cannot use P1. Then follow Creem Test acceptance steps 3–5 above.
4. **Stop and rollback:** Set `DECISION_REPORT_ENABLED=false` or remove it and redeploy Preview. Set the QA login back to NOLOGIN and PASSWORD NULL; have the operator close existing QA-only pool sessions (NOLOGIN alone does not revoke existing sessions). Remove its Preview URL and disable only the dedicated Test callback. Keep evidence and any ambiguous provider order claims until reconciled; then use the reviewable rollback SQL for only the named P1 tables/functions/schema/login. Do not touch production subscriptions, controls, or environment variables. DNS, pooler and live database grants were not verified by the local fixture.

Scoped fixture (disposable PostgreSQL via PGlite; no hosted connection): `PGLITE_MODULE=/absolute/prefix/node_modules/@electric-sql/pglite/dist/index.js node scripts/verify-decision-scoped-sql.mjs`. It proves positive order flow, refund replay, test UUID, role separation, and rejection of callable SECURITY DEFINER functions and PUBLIC table/column grants; it does not attest to actual hosted privileges. Supabase references: [Custom-role and PUBLIC privileges](https://supabase.com/kb/troubleshooting/custom-role-inherits-privileges-that-were-not-explicitly-granted-ddaa1c), [connection options](https://supabase.com/docs/guides/database/connecting-to-postgres).

### Scoped pooler TLS trust

The scoped PostgreSQL adapter uses the public Supabase Root 2021 CA bundled from [Supabase's production Dashboard download](https://supabase-downloads.s3-ap-southeast-1.amazonaws.com/prod/ssl/prod-ca-2021.crt) ([pinned Dashboard source](https://github.com/supabase/supabase/blob/8617532ae1a41571d5d557cd24c6f5f2565d9230/apps/studio/hooks/custom-content/custom-content.json)). The fixture asserts the DER SHA-256 fingerprint `807025ad50d4ed219d2c9c7d299c004f824eb00cf7f65afef607d07b72e6cafa`. Both the certificate chain and the configured hostname must validate; no environment variable or DSN option can turn this off. On rotation, compare the root with the authenticated project's Dashboard download and review the code and fingerprint update together. Do not trust a leaf from an unverified connection or disable validation. This root is local to the P1 pool only; other database or HTTP clients are unchanged.

### Canonical signed TEST ingress (requires separate activation)

The only signed TEST target is Git-connected `develop` Preview at `https://preview.goeast.ai`. The code requires `VERCEL_ENV=preview`, `VERCEL_GIT_COMMIT_REF=develop`, scoped PostgreSQL storage, the existing P1-only Test SKU, and the exact no-trailing-slash origin value `https://preview.goeast.ai`. Generated aliases are not accepted for TEST. The alternate QA branch may still run Mock; activating TEST requires the existing scoped credential and approved account to be securely configured for canonical `develop` Preview, without copying the app service-role key.

Only an authorized **dedicated** Creem TEST webhook can target `https://preview.goeast.ai/api/decision-report/webhook`, with its own signing secret and `checkout.completed` / `refund.created`. The webhook verifies the original bytes and limits both declared and streamed bodies to 64 KiB. This patch does not reconfigure or share the P0 webhook or credentials. The callback and checkout share the TEST feature flag; checkout is restricted by verified authentication to the designated QA UUID. Before creating any order, send the authorized provider dashboard sample only to this endpoint and verify normal signed ingress, the expected ignored response for a nonmatching sample, and unchanged QA order counts. This sequence requires no separate preflight flag. Green HTTP delivery alone is not entitlement.

A TEST refund only calls the QA database refund procedure after matching the designated owner, exact P1 SKU and both linked provider order and transaction. A signed refund with an explicit P1 SKU that is not yet linked retries; an unlinked refund with no P1 SKU is ignored without creating a tombstone and requires existing-order reconciliation if subsequently identified as P1. Do not open another checkout or override entitlement for an ambiguous outcome. Disable the TEST feature and redeploy Preview to stop accepting callbacks; production stays disabled.

### One-shot operator recovery of the existing sandbox attempt

Prefer an authoritative provider lookup/link over replay. Default state is off. Only for this single existing QA intent, when an operator decides that the provider evidence justifies trying the original request again, arm `DECISION_REPORT_RECOVERY_ENABLED=true`, `DECISION_REPORT_RECOVERY_ORDER_ID=<existing QA pending UUID>` and `DECISION_REPORT_RECOVERY_XMIN=<original xmin::text>` on **develop Preview only**. Do not refresh the pin to retry a failure. While armed, the configured QA owner must use the original synthetic cast on `https://preview.goeast.ai`; a changed or absent cast cannot create a new Test order.

The guarded PostgreSQL transaction checks the exact owner, cast, product, pending status, empty checkout/payment fields, and original version. Its no-op SQL update changes only the internal tuple version and commits before any provider call, consuming the pin. The existing checkout path then sends the original payload once, with redirects disabled, and links the validated response only to the consumed row version. An uncertain commit, lost provider response, or failed link is a stop for read-only reconciliation, not a second attempt. Disable the flag and redeploy after reviewing the same order. A one-shot database gate does not prove Creem reused the old session; no second cast, payment or model invocation is authorized by this step.
